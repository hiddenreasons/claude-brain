# Audit of main since 2026-10-04

Read-only review of every commit on `main` from `cee566b` (2026-10-09, the first commit; nothing on `main` is older than the cutoff) through `9a6911d` (2026-10-10). No application code was changed.

Only logic errors, security holes, offline breakage, data loss, and missing tests are listed. Ordered blocker, then major.

## 1. Blocker — a temp-file symlink is followed, and the file it points at is overwritten

- **Severity:** blocker
- **Commit:** `3333a88` (vault notes), `acd895a` (Brain folder pages)
- **Where:** `brain/obsidian.py:169`, `brain/brainfiles.py:78`
- **What:** Both atomic writers check the final path for a symlink, then open a predictable temp name (`.{note}.brain-tmp` in the vault, `.{page}.tmp` in `~/.vader-mac-runs/brain/`) with a normal write. `open` follows a symlink. If that temp name is already a symlink, the write truncates whatever it points at, including a file outside the vault or the Brain folder, and `os.replace` then makes the note or page itself that symlink. The next export treats the note as user-owned and stops updating it; the next Brain-folder write refuses the page because it is now a symlink. The outside file is already destroyed. Reproduced: a temp symlink to a file outside the tree was replaced with the generated text, and the note/page became the symlink.
- **Fix:** Create the temp file with `O_CREAT|O_EXCL|O_NOFOLLOW` (and `O_NOFOLLOW` on the final append/replace), in the same directory, and refuse if the temp path is a symlink or resolves outside the vault or Brain folder. Do not open it with `Path.write_text` or `open(path, "w")`.
- **Test:** Point `.RECOMMENDATIONS.md.tmp` and `.{note}.brain-tmp` at a file outside the folder, run `BrainFiles.write` and `VaultExporter._atomic_write`, and assert the outside file is unchanged, nothing outside the folder was written, and the real page/note is not a symlink. The existing symlink tests only cover the final path (`tests/test_guardrails.py`, `tests/test_obsidian.py`).

## 2. Major — the live page does not rebuild when the Windows heartbeat or a job worktree changes

- **Severity:** major
- **Commit:** `acd895a` (heartbeat and git resolution became inputs; the fingerprint they depend on is still the one from `cee566b`)
- **Where:** `brain/snapshot.py:57`
- **What:** `BrainState.refresh` rebuilds only when `fingerprint()` changes. That hash skips any runs-folder directory whose name starts with `_` or `.`, and it only stats the directory itself plus one level of children. `~/.vader-mac-runs/_xfer/win/heartbeat.json` therefore does not count: replacing or rewriting it in place leaves the fingerprint the same, so Windows job state and the "heartbeat under 12 min" self-check stay stale until some other file changes. A change inside `job/wt/` (a commit, or an edit of an existing file) also leaves the fingerprint the same, so a git resolution that should clear a blocked job does not show up on the live page. Reproduced for both an in-place heartbeat rewrite and an in-place edit of `job/wt/a.txt`.
- **Fix:** Stat `heartbeat.json` (and `brain/windows-status.json`, which is already covered) explicitly, and stat the worktree HEAD the git reader actually uses (`job/wt/.git`, or the gitdir it points at). Do not treat "the `wt` directory inode is unchanged" as "git did not move".
- **Test:** Write `_xfer/win/heartbeat.json`, rewrite it in place, and assert `fingerprint()` changes. Write `job/wt/a.txt`, rewrite it in place, and assert `fingerprint()` changes. `tests/test_snapshot.py` only checks a new `iter-1.jsonl` and the inbox.

## 3. Major — a naive timestamp makes the WINDOWS box go offline and hide its jobs

- **Severity:** major
- **Commit:** `7007f9e`
- **Where:** `brain/windows_status.py:39`
- **What:** A timestamp with no zone is interpreted as the Mac's local time. The heartbeat reader (`brain/machines.py`) treats the same shape as Eastern, which is what the Windows box writes. On a Mac whose zone is not Eastern those clocks disagree by the offset. Measured here (UTC vs Eastern): four hours. The box then sets `offline` once the computed age passes 15 minutes, and the page drops the job list and shows only "offline" (`brain/static/app.js:1493`). A fresh Windows machine looks down, and the other way around a stale copy can look live.
- **Fix:** Parse a zone-less stamp as `America/New_York`, the same rule as `machines._when`. Keep offsets and `Z` as written.
- **Test:** Feed `updated_at` of "now" in Eastern with no offset, call `read_windows_status` on a UTC clock, and assert `offline` is false and the running jobs are still listed. The current tests all use `iso()` or epoch, so they never hit a zone-less stamp.

## 4. Major — any comms line after `job_started` drops a remote job that is still running

- **Severity:** major
- **Commit:** `acd895a`
- **Where:** `brain/machines.py:200`
- **What:** The docstring says a remote job is one MAC started and has not logged as finished. The code keeps the job only when its latest comms line is still `job_started`. A later `reply` or `question` removes it. With an empty `running_jobs` list it is not added back from the heartbeat either. Reproduced: start only → the job is returned; start then reply → the list is empty. A real `job_finished` / `done` should still remove it.
- **Fix:** Remember whether a start has been seen and whether a later `job_finished`, `done`, or `report` has been seen. Keep the job while it was started and not finished. Do not require the latest line to be the start.
- **Test:** `remote_jobs` with `job_started` plus a later `reply` for the same Windows job, heartbeat not listing it, asserts the job is still returned and still `running`. A later `job_finished` asserts it is absent. No current test sends anything after the start line.

## 5. Major — a "Mark done" on an older one-shot stops working, and the alert comes back

- **Severity:** major
- **Commit:** `d57b2d1`
- **Where:** `brain/snapshot.py:266`
- **What:** Attention is built from every one-shot, then the snapshot keeps only the newest 150 (`ONESHOT_LIMIT`) and `marks.apply` runs on that slice. A stalled one-shot older than those 150 still sits in `attention`. Its mark is on disk, but it is not applied, so the alert comes back, the job shows no `owner_mark`, and the page has no Mark / Undo control (`findJob` only searches the slice). Reproduced with 151 stalled one-shots: the oldest stayed in `attention` after a matching mark, and no shown one-shot carried `owner_mark`.
- **Fix:** Apply marks to the full one-shot list before slicing, and build attention from the marked list. Keep the 150-row cap for the page payload only.
- **Test:** Create 151 stalled one-shots inside the 72-hour attention window, mark the oldest, rebuild the snapshot, and assert it is gone from `attention` and the mark is still in effect. Undo still restores that alert.

## 6. Major — approving or declining a lesson (or a recommendation) can be overwritten on the next refresh

- **Severity:** major
- **Commit:** `089c426` (recommendations), `6b69c08` (lessons)
- **Where:** `brain/advisor.py:98`, `brain/effects.py:58`
- **What:** The status Anthony or MAC sets is stored only in `RECOMMENDATIONS.md` / `PROPOSED-LESSONS.md`. A refresh reads it, then does the rest of the record (git, logs, other pages) and writes the page back from that old read. A save that lands in between is replaced with the previous status. An approval that took a job off Anthony's alert list, or a decline that stopped a false failure, is undone, and the markdown is the only copy. The write does re-read the file, but only to skip an identical rewrite, not to merge a newer status.
- **Fix:** Under the Brain-folder lock, re-read and parse the status lines immediately before building the new page. If the file changed after the first read, parse again and keep the new status and note. Same for the Fix line on a lesson.
- **Test:** Read a page whose status is `proposed`, change the file to `approved` before `write`, run `Recorder.record`, and assert the file still says `approved` and the snapshot treats the lesson as approved. Same for `applied` on `RECOMMENDATIONS.md`.

## 7. Major — a stalled one-shot is drawn as done on the timeline

- **Severity:** major
- **Commit:** `3070bd3`
- **Where:** `brain/timeline.py:75`
- **What:** Folder bars use lifecycle, and stalled maps to blocked. One-shot bars do not. Anything that is not `waiting`, `error`, or `blocked` is painted `done`, including `stalled` (no result for 6 hours), which is an alert everywhere else. Reproduced: a stalled one-shot produced a timeline bar whose state was `done`.
- **Fix:** Use the same lifecycle map as folder bars (`stalled` and `blocked` → blocked, `running` → running, `done` → done).
- **Test:** Build a timeline from one stalled one-shot and assert the bar state is `blocked`, not `done`.

## 8. Major — a Windows job that stalled, or that finished BLOCKED, is not shown as needing anyone

- **Severity:** major
- **Commit:** `0230ce8` (the node action). `d6b87c9` clears NEEDS ANTHONY after a mark on the comms fallback, which never runs once this node has claimed the id.
- **Where:** `brain/static/app.js:1141`
- **What:** `add()` keeps the first node for an id. Remote jobs are added first. A finished job has lifecycle `done`, so the action is `done` even when `source` contains `TO MAC: BLOCKED` (the case Mark done was added for). A heartbeat `stopped` / `failed` job has lifecycle `stalled`, which is not `blocked` and not `running`, so the action falls through to `queued`. The later comms loop would have marked a blocked line NEEDS ANTHONY, but `add()` ignores it because the id is already taken. The station shows a faint done dot or a queued dot, not the red marker, and a blocked Windows job drops off after a day like a success.
- **Fix:** If there is no owner mark and the source or last text contains `TO MAC: BLOCKED`, use `needs_anthony` even when lifecycle is `done`. Map lifecycle `stalled` to `needs_anthony`, not `queued`. Let a blocked comms line replace a `done` node for the same id.
- **Test:** Build the Windows node list (the same way `tests/js/vaderlink.test.js` pulls a helper out of `app.js`) for a remote job with lifecycle `done` and a BLOCKED source, and assert the action is `needs_anthony`. A second case with lifecycle `stalled` asserts `needs_anthony`, not `queued`. After `owner_mark`, assert `done`.

## What this pass could not check

- **Webhook redirects.** Nothing in this repo, or in its history, sends a webhook, sets a `Location` header, or redirects. There is no redirect to test.
- **API keys and other secrets in live files.** The code never reads an API key, bearer token, or `Authorization` header. It does copy Claude `session_id` and report/result text into the snapshot and into Obsidian notes. The real `~/.vader-mac-runs` job files and the vault are not in the repo, so this pass could not see whether a report already contains a key the page would then show.
- **CSRF from a second browser origin.** `POST /api/mark` requires a loopback `Host`, a matching loopback `Origin`, `X-Brain-Action: mark`, and a JSON content type (`brain/server.py:289`), and `tests/test_marks.py` covers a cross-site body smuggled onto a kept-alive connection. That was not replayed from a page loaded on another origin.
- **Anthony's live MAC, Windows, and VADER files.** Heartbeat age, inbox shape, and worktree layout were checked against the code and fixtures, not against the copies on his Mac. The four-hour offline skew was measured with this environment's UTC clock.
- **The full pytest and node suites.** Targeted snippets covered the findings above. The suites were not run end to end.
